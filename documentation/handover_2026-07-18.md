## What this project is

UoE MSc dissertation: a Physics-Informed Neural Network (PINN) predicting Sitka spruce top-height
growth at Aberfoyle forest, using LiDAR survey data (4survey and 6survey cohorts). The PINN
combines a plain neural network with a Chapman-Richards (CR) growth-curve physics constraint. The
dissertation's actual goal is **growth attribution** (explaining *why* plots differ, via terrain
and wind exposure), not a prediction-accuracy competition — see
`documentation/plans_md/Dissertation Plan v5 - 7th June.md`.

## What's been built and run so far

**Four baselines** (Chapman-Richards, average-by-age, linear regression, random forest) — fitted
and evaluated under all three split types: `plot_level_split` (easy, random), `spatial_block_split`
(whole compartments held out — **the dissertation's primary split**, decided because planned
environmental covariates are static per-plot, not year-varying), and `temporal_split` (train on
earliest years, test 2023 — secondary but real).

**DNN and PINN, no-environment feature set** (age + thinning only) — built, tuned, and evaluated:

## Key findings (the ones that matter for the write-up)

1. **DNN and PINN both beat every baseline**, under both `spatial_block` (primary) and `temporal`
   (secondary), by a real margin (PINN vs. CR: -16%/-9% RMSE under spatial_block, -22%/-15% under
   temporal).
2. **DNN robustly wins 4survey; DNN and PINN are tied within noise on 6survey** — revised
   2026-07-20 after a multi-seed reseed check (previously reported as "DNN wins 4survey, PINN wins
   6survey," which turned out not to survive a different seed on the 6survey side — see
   `experiment_log.md`'s 2026-07-20 entries). PINN's real, established advantage is **training
   stability** (no overfitting collapse in any tested configuration, confirmed across every reseed
   too), not lower error anywhere.
3. **The physics constraint hurts at full weight, and that's informative, not a failure.**
   Chapman-Richards uses one global `y_max` for every plot; forcing the network to match it as
   strongly as it matches real data fights against real plot-to-plot variation — exactly the
   variation this dissertation exists to explain. This is *why* DNN needs to stay in the comparison
   at every future stage (the necessary "same features, no physics" control), not be dropped now
   that "PINN looks competitive."
4. **This connects directly to Yield Class.** Forest Research's `yldc` (General Yield Class) is
   the industry-standard version of the same idea as CR's `y_max` — Aberfoyle's typical Sitka GYC
   range (8–20) implies a CR `y_max` of ~28–50m. Worrell (1987, already cited in the dissertation
   plan) found Yield Class varies substantially with terrain in Scottish upland sites — meaning a
   single assigned Yield Class per stand is probably too coarse, the same gap the weight sweep
   found empirically. **Env-PINN's plot-specific `y_max(terrain, wind)` is effectively re-deriving
   Yield Class at finer resolution than Forest Research currently assigns it** — this is the
   sharpest way to frame the dissertation's contribution to a forestry audience.
5. **Spatial error maps show the same error clusters across all six models**, in the same two
   locations (not model-specific) — suggests a genuinely hard region or data-quality issue in
   specific compartments, not something any current model handles differently. Worth identifying
   which compartments before building Env-PINN.
6. Why PINN is still justified despite point 2: this dissertation is explicitly **not** a
   prediction-accuracy competition (see the plan) — it's about attribution, which only PINN's
   physics-anchored architecture can provide once `y_max` becomes plot-specific. DNN can't produce
   that output regardless of its accuracy.

## Working conventions worth knowing

- **`documentation/experiment_log.md`**: add one row per experiment config; update in place for
  reruns of the same config, don't duplicate rows. Timestamps now include time-of-day (adopted
  2026-07-18), not just date.
- **Cluster sync**: always rsync the *whole* `outputs/` and `logs/` directories (not sub-paths) —
  a recurring past mistake was syncing only part of what changed.
- **Submitting a batch of cluster jobs**: write the `for`-loop of `sbatch ...` commands to a
  scratch `.txt` file (convention as of 2026-07-20: `documentation/sbatch_scripts/`), then on the
  cluster run `bash documentation/sbatch_scripts/<file>.txt` — bash doesn't care about the `.txt`
  extension, this just executes the loop and fires every `sbatch` call. Delete the file once
  submitted; it's scratch, not a permanent artifact.
- **Don't run git commands unless explicitly asked** — the user commits/pushes manually.
- **Code style**: beginner-friendly (W3Schools-tutorial style), not idiomatic/compressed Python —
  this applies to `models/` and analysis scripts.
- **Notebooks**: after any edit, re-execute with
  `jupyter nbconvert --to notebook --execute --inplace <notebook>.ipynb` and check for zero errors
  before considering it done. If a notebook grows too large for the `Read`/`NotebookEdit` tools
  (embedded chart images push it over the token limit), `jupyter nbconvert --clear-output --inplace`
  first, edit, then re-execute to regenerate outputs. Direct Python/JSON manipulation of the
  `.ipynb` file is a reliable fallback when `NotebookEdit` itself won't work on a large file.
